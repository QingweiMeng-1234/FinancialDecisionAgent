为了验证这个判断，我做了一个很轻量的 retrieval sanity check，用同一家公司跑多种 query 形式，比如 MSFT、Microsoft、Azure、Satya Nadella。
在当时那批数据里，MSFT 命中是 0，Microsoft 只有 1，Azure 和 Satya Nadella 也是 0，
而且唯一命中的那篇文章也是写 company name、不写 ticker。这让我基本确认，ticker-only retrieval 本身就不稳定，系统缺一个把 ticker、company name 和 aliases 统一起来的 identity layer。”

“接着我为了更系统地验证这个问题，开始做 retrieval eval 和 golden set 标注。
结果标注过程中我又发现第二个更底层的问题：库里很多数据只有 summary，没有 canonical full text。
这样即使是我自己做人标，也很难稳定判断一篇文章到底该算 relevant 还是 non-relevant，因为 summary 是压缩后的二手信息，很多实体线索、事件细节和语气都已经丢掉了。
所以我最后把问题拆成两层来看：第一层是缺 knowledge base，导致 entity identity 不稳定；
第二层是缺原文，导致不仅 retrieval 弱，连 retrieval evaluation 本身也不可靠。也正因为这样，我后面不是只补 knowledge base，而是同时推进了 article full-text backfill，
把 identity layer 和 content layer 一起补起来。”

要做这个 knowledge base，核心原因只有一句：

现在系统知道“ticker 代码”，但还不知道“这个 ticker 在现实世界里是谁”。

这会直接卡住你项目往工业级走的几条关键路径。

1. 解决检索入口太弱的问题（召回低）
现在如果只拿 MSFT 去找新闻，会有两个常见问题：

漏召回：新闻里写的是 Microsoft、Azure，不写 MSFT
错召回：语义相近但其实和 MSFT 无关的内容也可能被拉进来
所以单 ticker 检索不稳。
knowledge base 的作用，就是把：

ticker
company_name
aliases
以后可能还有 products / business lines / common mentions
绑成一个稳定的“身份包”。

这样系统检索的不是一个代码，而是一个被定义清楚的实体。

2. 解决 triage 判断不可信的问题
你现在的 why_now / key_evidence / counter_evidence 看起来已经很像产品了。
但如果底层证据本身经常拿错，这些上层判断再漂亮也不稳。

也就是说：

没有 identity layer，triage 是建在松土上
有了 knowledge base，triage 才开始有“证据属于谁”的基础
3. 解决 watchlist 设计会空转的问题
你前面已经意识到了这一点：

watchlist 回答的是“我想看什么”
knowledge base 回答的是“这个 ticker 到底是谁”
如果连“是谁”都没定义清楚，先做 watchlist 只会把输入做得更漂亮，但 retrieval 还是可能错。

所以顺序应该是：

knowledge base
retrieval identity matching
watchlist context
triage / reviewer

4. 这是工业级项目里的真实子系统，不是为了复杂而复杂
工业级系统很少直接把用户输入裸用到底。
中间通常都会有一层“规范化/实体层”，比如：

用户名 -> 用户实体
商品 ID -> 商品目录实体
ticker -> 金融标的身份实体
你的 knowledge base 就是这层实体层。

它能让你以后回答很像工业项目的问题：

为什么不能直接用 ticker 做检索？
怎么处理公司名、简称、别名、产品名？
怎么减少 ticker 相关性的误判？
怎么验证“这条新闻真的是这个 ticker 的”？
这些都是面试里很值钱的问题。

5. 它能带来可量化改进
做完后你可以明确评估：

ticker-specific article hit rate
false positive rate
top-k relevance
watchlist triage 的 specificity rate
这就不是“我感觉更准了”，而是“我有一个 identity layer，把相关性质量拉上去了”。

耦合，一次性的本质是不是前期从0到1的时候只是注重是实现了什么功能，而并没有重视怎么建立data pipeline

一个对象同时承担 identity、content、summary、indexing 多种职责

后面需求一复杂，就发现这条链路其实是一次性的
所以“耦合、一次性”的本质，很多时候确实不是因为设计者不懂，而是因为在 0 到 1 阶段，优化目标根本不是 pipeline quality，而是 feature existence。

0 -> 1


是否要存raw data?

如果经过 cleaning/normalization 之后还能无损支撑未来所有需求，那 raw data 不一定要存。
如果清洗后会丢信息，而这些信息未来可能有价值，那最好存 raw data 或某种 canonical 原始版本。

你可以把场景分成三类：

1. 强烈建议存 raw data

以后可能要重跑抽取/特征工程
清洗步骤不可逆
需要审计、追溯、debug
上游数据源不稳定、不可重复获取
这次文章 pipeline 就接近这一类。
虽然我们最后没存 raw_html，但我们至少存了 canonical full text，因为如果连这个都不存，后面 summary/vector 全部失去可重建基础。

2. 可以不存 raw data

上游数据本身稳定且可随时重取
清洗是近乎无损的
raw data 很大但价值不高
业务只关心标准化后的结果

Before
系统将 NewsAPI 返回的 title + description 直接当作文章内容写入 SQLite，并基于这份短文本生成 summary、向量和检索结果。上游线索、正文真相和下游派生产物被混在同一条线性处理链路中，导致全文缺失、数据职责不清、下游结果建立在不完整输入上，且系统缺乏真正的重建能力。

After
系统先用 URL 建立 article identity，再从 publisher 页面抓取并抽取 exact content，将正文落盘为 data/articles/{article_id}.txt，并由 SQLite 维护 URL、内容路径、hash 和处理状态。summary、chunk vectors 和 retrieval evidence 都从这份 canonical full text 派生生成。这样数据流被重构为 article-centric、分层、可重建的 pipeline：上游 signal、canonical content 和 derived artifacts 各自职责清晰，且下游阶段可以独立失败、独立重试、独立重建。

解耦架构：

解耦成了三份：

1. News URL -> Original Content -> Derived Content

每一步都有可能失败，尤其是 News URL -> Original Content这种类似于RPC的call非常容易失败。

这种解耦让问题的归属更明确


对，这个表述很准，而且已经抓到这次改动最重要的工程意义了。

你现在其实可以把系统抽象成这三层：

News URL
Original Content
Derived Content
也就是：

News URL
  -> Original Content
  -> Derived Content
其中：

News URL
负责 article discovery / identity
解决“这篇文章是谁”
Original Content
负责 canonical text
解决“这篇文章原文是什么”
Derived Content
负责 summary / chunks / vectors / retrieval evidence
解决“我们基于这篇文章算出了什么”
你说“News URL -> Original Content 很像 RPC call，非常容易失败”，这个判断也非常对。因为这一步天然依赖外部世界：

publisher 页面能不能访问
有没有重定向
页面结构是否可抽取
网络是否稳定
反爬、超时、403、空正文
canonical URL 解析是否成功
所以这一步不是本地纯函数，而是一个外部依赖的、不稳定的 acquisition step。
这意味着它和后面的 Original Content -> Derived Content 本质上不是同一类操作。

后者通常更像本地计算：

summary 生成
chunking
embedding
retrieval shaping
它们当然也会失败，但失败性质不一样：

更多是模型失败、资源失败、逻辑失败
而不是“外部文章根本拿不到”
所以你这次解耦的价值，正是在于把两类失败隔开了。

以前没解耦时，系统看到的只是：

“这条新闻处理失败了”
但现在可以明确知道是：

URL 级失败：找到了文章线索，但没拿到正文
Original Content 级成功，但 Derived Content 失败：正文已有，只是摘要/索引还没生成
这就带来你说的那句非常重要的话：

这种解耦让问题的归属更明确。

更具体一点说，它让问题归属从“整条 pipeline 黑盒失败”变成了“明确定位在哪一段失败”：

News URL -> Original Content 失败
问题归属到抓取/抽取层
不该怪 summary 或 vector
Original Content -> Derived Content 失败
问题归属到派生计算层
不该怪 URL ingestion
这也是为什么状态字段现在很关键：

content_status
表示 URL -> Original Content 这一步是否成功
summary_status
表示 Original Content -> Summary 是否成功
index_status
表示 Original Content -> Chunks/Vectors 是否成功
这三者本质上就是把“问题归属”编码进数据模型里了。

如果你想把这段写得更像设计文档，我建议可以直接写成：

Before
旧架构中，新闻线索获取、正文内容获取和下游派生计算被串联在同一条线性流程里，失败会表现为统一的“文章处理失败”，难以区分究竟是上游抓取问题、正文缺失问题，还是下游摘要/索引问题。

After
新架构将流程解耦为三层：News URL -> Original Content -> Derived Content。其中 News URL -> Original Content 是一个依赖外部页面获取与抽取的高不稳定步骤，而 Original Content -> Derived Content 则是基于 canonical text 的本地派生计算。通过将这两类步骤分离，并为每一阶段单独维护状态，系统可以更准确地定位失败归属，使抓取失败、摘要失败、索引失败各自拥有清晰边界和独立重试路径。

2. 把 query 发给 DuckDuckGo HTML 搜索页

-----------------------------------------------------------------
为什么不用LLM？
这里我们做的是很机械的 HTML 提取：

找搜索结果链接
提取 <a class="result__a" href="...">标题</a>
拿到 url 和 title
这类任务用正则或 HTML parser 更合适，原因有几个。

规则很固定
DuckDuckGo HTML 页面的结果结构比较稳定，提取链接属于结构化解析，不是模糊理解。LLM 在这里没有明显优势。

可控性更强
正则/解析器是确定性的：

同样输入，同样输出
方便调试
出错位置明确
-------------------------------------------------
第二段：怎么从 potential candidates 里选最终 candidate

入口在 backfill_record()。

它的做法是：

对第一个 query 搜索
拿到这一批 candidates
对这一批 candidates 全部打分
如果已经有分数超过阈值的最佳项，就先用它
如果没有，就继续跑下一个 query
把多个 query 的结果合并，再从总池子里选最佳项
也就是说，它不是“看到第一个搜索结果就用”，而是：

先召回一批 -> 对每个候选打分 -> 选分最高的

--------------------------------------------------
怎么打分的？

分数组成
当前分数主要由三部分构成。
标题相似度
这是主分项，也是最重要的一项。
在 backfill_source_urls.py 的 title_similarity() 里，脚本会先把两边文本标准化：
全部转小写
非字母数字字符变空格
多余空格折叠
然后用 Python 的 SequenceMatcher 算字符串相似度。

描述重合度
如果候选也有 description，就会加：
0.15 * description_overlap(...)

发布者匹配奖励/惩罚
这是为了减少误匹配。

然后把 publisher 切成 token，比如：

ars
technica
politico
wsj
见 publisher_tokens()。

接着检查这些 token 是否出现在候选的：

source_name 域名
candidate.title
见 publisher_matches_candidate()。

规则是：

匹配上：+0.08
明显不匹配：-0.35

先从原标题里抽 publisher hint
标准化之后把 publisher hint 切成 token，然后切去常见词。
检查切出来的token是不是在publisher_hint(retrieved from DB)里面，只要有一个token match上了就算match上
