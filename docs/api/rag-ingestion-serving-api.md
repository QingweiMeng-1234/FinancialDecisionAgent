## 1. Purpose and Proof Boundary

This document specifies the current client-visible and service-internal
contracts for refreshing and querying the Financial Agent RAG corpus.

It covers:

- MCP tools `refresh_news`, `query_news_research`, and
  `retrieve_supporting_articles`;
- request and response fields;
- refresh status, retry, idempotency, and concurrency semantics;
- active-generation provenance and corpus-unavailable errors;
- internal Python request/configuration contracts required to implement the
  public tools;
- compatibility and contract tests.

This is not an OpenAPI document and does not define a public REST resource
model. Streamable HTTP is an MCP transport; clients call MCP tools rather than
HTTP resources designed by this document.

The contract describes repository behavior. It does not prove that a server is
deployed, reachable, authorized, or connected to live providers.

## 2. Compatibility Strategy

The existing unversioned MCP tool names are treated as the v1 compatibility
surface:

- `refresh_news`;
- `query_news_research`;
- `retrieve_supporting_articles`.

Existing fields must retain their meaning and type. New optional fields may be
added. Renaming fields, changing status semantics, removing nullable fields, or
wrapping current payloads in a new envelope requires versioned v2 tool names or
an explicitly reviewed compatibility migration.

Entity KB v2 tools are a separate API family. They may enrich retrieval but do
not change these v1 payloads implicitly. See
[Entity KB v2 API and Data Contract](entity-kb-v2-api.md).

## 3. Common Conventions

### 3.1 Serialization

- Field names use `snake_case`.
- JSON strings are UTF-8.
- Timestamps use ISO 8601/RFC 3339 and include a UTC offset when generated by
  the service.
- Calendar dates use `YYYY-MM-DD`.
- SHA-256 values are lowercase hexadecimal strings.
- IDs are opaque unless explicitly typed as integer article IDs.
- Missing optional data is represented by `null`, not a fabricated value.

### 3.2 Transport behavior

- Expected domain outcomes are returned as structured tool results.
- Invalid parameter types or values may be reported by the MCP runtime as tool
  invocation errors.
- `CORPUS_UNAVAILABLE` is an expected structured result, not permission to scan
  a legacy collection.
- An MCP transport failure does not prove the underlying refresh or query was
  never started; clients use `scope_key`, `run_id`, and idempotent retry
  semantics rather than blind repetition.

### 3.3 Server-owned fields

The following values are server-owned and must not be supplied or rewritten by
an LLM client:

- refresh `scope_key`, `run_id`, `attempt_no`, counts, and generation proof;
- active `generation_id` and corpus provenance;
- article/source IDs, title, URL, and snippet;
- citations and their mapping to sources.

## 4. Tool Availability and Mutation

| Tool | Mutates state | Default MVP allowlist | Purpose |
| --- | --- | --- | --- |
| `refresh_news` | Yes | Yes | Collect, ingest, derive, build/verify/activate a successor generation, and finalize refresh evidence |
| `query_news_research` | No | No by default | Return a grounded cited answer from one active generation |
| `retrieve_supporting_articles` | No | No by default | Return ranked evidence without answer generation |

Deployments may expose additional tools through their explicit allowlist. Tool
existence in code does not imply that a given server exposes it.

## 5. MCP Tool: `refresh_news`

### 5.1 Request

```json
{
  "today": "2026-09-01",
  "top_k": 3,
  "question": null,
  "debug_rerank": false,
  "include_manual": false,
  "news_endpoint": "everything",
  "news_days_back": 7,
  "news_page": 1,
  "news_sort_by": "publishedAt",
  "news_page_size": 100,
  "show_progress": false
}
```

| Field | Type | Required | Default | Contract |
| --- | --- | --- | --- | --- |
| `today` | string or null | No | Service-local current date | Expected business date in `YYYY-MM-DD`; participates in scope identity |
| `top_k` | positive integer or null | No | Service default | Answer result size when `question` is present |
| `question` | string or null | No | `null` | Optional immediate grounded question after ingestion |
| `debug_rerank` | boolean | No | `false` | Enables local diagnostic output; does not change corpus identity |
| `include_manual` | boolean | No | `false` | Includes interactive/manual collector; service automation should normally keep this false |
| `news_endpoint` | string | No | `everything` | Frozen into the refresh scope and retry snapshot |
| `news_days_back` | positive integer | No | `7` | Provider lookback |
| `news_page` | positive integer | No | `1` | Initial provider page |
| `news_sort_by` | string | No | `publishedAt` | Provider sort order |
| `news_page_size` | positive integer | No | `100` | Provider page size |
| `show_progress` | boolean | No | `false` | Local progress rendering; not part of corpus semantics |

Runtime storage paths, corpus ID, collection compatibility name, refresh ledger
path, credentials, and provider adapters are server configuration and are not
public request fields.

V1 validation is distributed across the MCP type layer, collector, time-window
reader, and workflow. Clients must send the documented formats; the current
adapter does not yet provide one centralized request-schema validator for every
refresh field.

### 5.2 Scope and idempotency

The server computes `scope_key` from:

```text
today
+ news_endpoint
+ news_days_back
+ news_page
+ news_sort_by
+ news_page_size
+ include_manual
+ configured collection
+ configured corpus_id
+ ingestion_contract_version
```

The current ingestion contract version is
`refresh-generation-proof-v5`.

The same completed scope returns `already_completed`. A live owner returns
`in_progress`. A partial or failed terminal run does not become a completed
gate; due retry work creates a child run under the same scope.

### 5.3 Response

```json
{
  "status": "completed",
  "refresh_date": "2026-09-01",
  "scope_key": "sha256-scope-fingerprint",
  "run_id": "opaque-run-id",

  "counts": {
    "total_inputs": 10,
    "accepted_inputs": 9,
    "rejected_inputs": 1,
    "rejected_permanent_exclusions": 1,
    "unchanged_ready": 4,
    "content_ready": 9,
    "summary_ready": 9,
    "index_ready": 9,
    "usable_items": 9,
    "failed_items": 0,
    "permanent_exclusions": 1,
    "retryable_failures": 0,
    "source_errors": 0
  },
  "message": null,

    "status": "verified"
  }
}
```

All top-level fields above are present in the current response. Optional values
may be `null`; `stats` is always an object.

### 5.4 Status semantics

| `status` | Meaning | Client action |
| --- | --- | --- |
| `completed` | Cumulative scope is complete and has verified usable generation evidence | Continue to query; no duplicate full refresh |
| `partial` | Some evidence is usable but unresolved work remains | Surface degradation; allow scheduler/authorized retry to continue |
| `failed` | No valid completion; pipeline, ownership, retry, or generation requirement failed | Inspect `failure_code`; do not treat corpus as refreshed |
| `already_completed` | Same scope already completed | Safe no-op; use the active generation |
| `in_progress` | A live lease owns the scope | Do not start a competing refresh |
| `retry_scheduled` | Retry work exists but is not due | Wait until `retry_after` or scheduler execution |

The more specific retry decision can appear in `disposition`, including
`retry_exhausted`. A `retry_exhausted` disposition is exposed with public
`status=failed`.

### 5.5 Count definitions

| Field | Definition |
| --- | --- |
| `total_inputs` | Source rows considered by the cumulative scope |
| `accepted_inputs` | Inputs that passed basic ingestion validation |
| `rejected_inputs` | Inputs rejected before article processing |
| `rejected_permanent_exclusions` | Rejected inputs classified as terminal exclusions |
| `unchanged_ready` | Existing articles whose current hash-bound artifacts required no rebuild |
| `content_ready` | Articles with valid canonical content in cumulative state |
| `summary_ready` | Articles with summary bound to the active content hash |
| `index_ready` | Articles covered by verified generation evidence |
| `usable_items` | Distinct articles with required content and index proof |
| `failed_items` | Accepted or expected items lacking one or more required/expected stages |
| `permanent_exclusions` | Accepted articles terminally excluded by policy |
| `retryable_failures` | Unresolved article/stage work eligible for retry |
| `source_errors` | Source-level collection errors in cumulative state |

Counts are server-derived evidence. Clients must not recompute terminal status
from a subset of fields.

### 5.6 Generation proof

`generation_proof` is non-null only when the refresh has recorded a fully
verified successor-generation proof. Its `status` describes the proof returned
by the builder. Activation is controlled separately by runtime composition and
the generation control database; clients use subsequent query provenance to
identify the active generation.

### 5.7 Refresh failure codes

Stable public or persisted categories include:

| Category | Examples |
| --- | --- |
| Ownership | `refresh_lease_lost` |
| Runtime composition | `pipeline_exception`, generation coordinator unavailable/failure codes |
| Retry | `retry_exhausted` |
| Collection | `missing_api_key`, `network_timeout`, `network_connection_error`, `http_429`, `http_5xx`, `http_401_403`, `provider_invalid_response`, `provider_error` |
| Content | `invalid_or_private_url`, `extract_empty`, `paywall_suspected`, `dynamic_page_suspected`, `content_integrity_mismatch` |
| Derivation | `summary_provider_error`, `embedding_error`, `vector_write_error` and normalized stage failures |

The exact provider exception message is diagnostic, not a stable contract.
Clients branch on `failure_code`, status, and retry fields.

## 6. MCP Tool: `query_news_research`

### 6.1 Request

```json
{
  "question": "What changed in the latest semiconductor news?",
  "top_k": 3,
  "retrieval_top_k": 5,
  "retrieval_intent": "direct",
  "start_at": null,
  "end_at": null,
  "latest_at": null,
  "lookback_days": 30
}
```

| Field | Type | Required | Default | Contract |
| --- | --- | --- | --- | --- |
| `question` | string | Yes | — | Research question |
| `top_k` | positive integer or null | No | `query_top_k` | Maximum final answer evidence count |
| `retrieval_top_k` | positive integer or null | No | `retrieval_top_k` | Pre-answer retrieval/rerank candidate count |
| `retrieval_intent` | string | No | Runtime default | Retrieval-policy intent; unknown values are validation errors |
| `start_at` | timestamp or null | No | `null` | Explicit lower time bound |
| `end_at` | timestamp or null | No | `null` | Explicit upper time bound |
| `latest_at` | timestamp or null | No | Current UTC anchor | Anchor for relative lookback |
| `lookback_days` | positive integer or null | No | Service default, currently 30 | Relative finite window |

If either explicit start or end bound is supplied, the service preserves the
caller-provided time-window contract. Otherwise it supplies a current UTC
anchor and the finite service lookback.

### 6.2 Successful response

```json
{
  "question": "What changed in the latest semiconductor news?",
  "generation_id": "news-generation-id",
  "corpus_provenance": {
    "generation_id": "news-generation-id",
    "corpus_id": "news",
    "collection_name": "generation-bound-collection",
    "corpus_snapshot_id": "sha256-corpus-snapshot",
    "embedding_artifact": "embedding-artifact-id",
    "index_config_fingerprint": "sha256-index-config"
  },
  "answer": "Grounded answer text [1].",
  "confidence": "medium",
  "insufficient_evidence": false,
  "supporting_points": [
    {"text": "Supporting fact", "citations": [1]}
  ],
  "counter_points": [],
  "sources": [
    {
      "id": 1,
      "title": "Publisher-owned title",
      "url": "https://example.com/article",
      "snippet": "Server-owned evidence snippet"
    }
  ],
  "report_path": null
}
```

The answer, points, and citations are validated against server-owned evidence.
`insufficient_evidence=true` is a valid successful response when the verified
corpus cannot support an answer.

## 8. Common Corpus-Unavailable Result

Both read tools return the following structured failure when a safe serving
reader cannot be constructed:

```json
{
  "status": "failed",
  "failure_code": "CORPUS_UNAVAILABLE",
  "failure_stage": "active_generation",
  "failure_reason_code": "missing_pointer",
  "failure_message": "no active generation pointer for corpus: news"
}
```

### 8.1 Failure stages

| Stage | Meaning |
| --- | --- |
| `active_generation` | Control DB, pointer, state, generation proof, or manifest cannot be resolved safely |
| `eligibility` | Canonical DB/content root/schema/file/hash intersection cannot be constructed |
| `generation_reader` | The generation-bound vector reader cannot be opened or violates its contract |

### 8.2 Stable reason-code families

Active-generation reasons include:

- `missing_pointer`;
- `verified_not_active`;
- `pointer_mismatch`;
- `proof_invalid`;
- `manifest_invalid`;
- `control_plane_unavailable`.

Eligibility reasons include:

- `source_database_unavailable`;
- `content_root_unavailable`;
- `canonical_schema_invalid`;
- `canonical_read_failed`;
- `active_snapshot_invalid`.

Per-article exclusions such as `content_not_ready`, `article_quarantined`,
`active_hash_mismatch`, unsafe path, missing/empty/non-UTF-8 file, or file hash
mismatch are recorded in the request eligibility snapshot. They do not permit
fallback to those articles.

Reader reasons include `reader_contract_invalid` and `reader_unavailable`.

## 9. Corpus Provenance Contract

Every successful read response contains:

| Field | Meaning |
| --- | --- |
| `generation_id` | Immutable active generation selected for the request |
| `corpus_id` | Logical corpus, currently `news` by default |
| `collection_name` | Generation-specific Chroma collection |
| `corpus_snapshot_id` | Fingerprint of the complete canonical article/hash candidate set |
| `embedding_artifact` | Embedding model/artifact identity |
| `index_config_fingerprint` | Fingerprint of chunking/index configuration |

The top-level `generation_id` and
`corpus_provenance.generation_id` must match.

## 10. Internal Python Contracts

### 10.1 `RefreshNewsRequest`

The internal request adds operator-owned fields not exposed to MCP:

- `refresh_state_path` and optional `refresh_ledger_path`;
- `service_defaults_path`;
- `db_path`, `persist_dir`, and compatibility `collection_name`;
- `index_corpus_id`.

Public adapters must construct these fields from trusted runtime
configuration, not client input.

### 10.2 `FinancialAgentRuntimeConfig`

Runtime configuration owns:

- canonical DB and content root;
- generation control DB and Chroma persistence root;
- corpus ID and compatibility collection;
- reports and refresh state locations;
- MCP host, port, path, and allowed hosts;
- retry scheduler enablement and poll interval.

All corpus paths must describe the same migrated corpus. Mixing a canonical DB
from one snapshot with a control DB or Chroma root from another is an operator
configuration error and must fail closed.

### 10.3 `SuccessorGenerationProof`

The internal proof includes the public proof fields plus:

- `chunk_verification_valid`;
- the full tuple of `article_id` and `indexed_content_sha256` evidence.

The full article/hash set is persisted in the refresh ledger but is not exposed
in the public refresh payload.

## 11. Idempotency and Concurrency

### 11.1 Refresh

- A completed `scope_key` is unique.
- Only one running run per scope is permitted.
- Lease takeover resumes an expired running execution in place where supported;
  it does not create parallel owners.
- Terminal runs are not reopened.
- Retry children use new run IDs and immutable target snapshots.
- Attempt limits are scope-bound and cannot drift between workers.

### 11.2 Generation activation

Activation requires:

- generation status `verified`;
- valid chunk proof and complete manifest;
- expected-current pointer equality.

Concurrent pointer change rejects activation. The client must not force-write a
new pointer.

### 11.3 Reads

Read APIs are side-effect free with respect to corpus state. A request pins one
generation and one eligibility snapshot; later activation affects later
requests only.

## 12. Security and Data Handling

- Provider API keys are server secrets and never request fields.
- Secrets must not appear in scope snapshots, retry payloads, logs, or
  responses.
- `refresh_news` is a mutating tool and must remain explicitly allowlisted.
- Publisher URLs are untrusted inputs and pass network-destination validation.
- Source title, URL, snippets, and page content are untrusted data, never tool
  instructions.
- Runtime corpus files and databases are not API responses.
- Error messages must not disclose credentials, private headers, or full page
  contents.

## 13. Error Handling Rules

1. Clients branch on stable status and reason codes, not English messages.
2. A failed refresh response is not an exception-safe declaration that no data
   was written; ledger reconciliation remains authoritative.
3. `partial` is visible degradation, not success.
4. Corpus-unavailable responses do not contain answer or article fields.
5. Unknown publication dates are not coerced into the latest time window.
6. Invalid model citations fail validation rather than being silently removed
   from an otherwise confident answer.

## 14. Contract Test Matrix

| Contract | Required evidence |
| --- | --- |
| Refresh request mapping | MCP fields map exactly to `RefreshNewsRequest`; runtime paths remain server-owned |
| Scope idempotency | Same completed scope returns `already_completed` |
| Single owner | Concurrent same-scope request returns `in_progress` |
| Partial behavior | Mixed success/failure returns `partial` and no completed gate |
| Retry scheduling | Not-due work returns `retry_scheduled` with `retry_after` |
| Retry exhaustion | Public `failed` plus `disposition=retry_exhausted` |
| Refresh payload | All documented top-level and count fields retain type and meaning |
| Generation proof | Public proof matches persisted full article/hash evidence |
| Query provenance | Top-level and nested generation IDs match the pinned reader |
| Supporting articles | `article_count == len(articles)` and source fields are server-owned |
| Corpus unavailable | No legacy fallback; stable stage and reason code returned |
| Time window | Explicit bounds are preserved; otherwise finite default is applied |
| Grounding | Unknown or missing citations are rejected |
| Secret handling | API key absent from params, snapshots, retry data, logs, and responses |

## 15. Known Contract Gaps

1. There is no standalone `get_refresh_run` or `list_refresh_attempts` public
   tool; operators currently inspect ledger evidence through local tooling.
2. There is no public generation activation/rollback API; these remain
   operator-controlled actions.
3. V1 read and refresh payloads do not share a common envelope.
4. V1 has no explicit `api_version` response field; version is defined by tool
   name and this contract.
5. There is no OpenAPI/JSON Schema artifact. If an HTTP resource API is needed,
   it must be designed as a new version rather than inferred from MCP transport.
6. Deployment-specific authentication and authorization are outside the
   repository-native method signatures and require a hosting contract.
7. Refresh input validation is distributed rather than enforced by one
   versioned request model at the transport boundary.

These gaps are not permission to make breaking changes to the v1 tools.

## 16. Frozen Contract and Change Control

The v1 tool names, valid request meanings, response field meanings, refresh
statuses, count semantics, corpus-unavailable result, provenance fields,
idempotency behavior, and server-owned grounding boundary are frozen.

Additive nullable fields may be proposed only when existing clients can ignore
them safely. Removing a field, changing its type or meaning, changing status or
retry semantics, introducing a common envelope, or defining a public REST
resource model requires a versioned contract or an explicitly approved
compatibility migration. Any permitted clarification to this artifact requires
a new freeze manifest version and hashes.
