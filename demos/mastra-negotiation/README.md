# Mastra 多 Agent 对照实验

三个同页、本地运行的对照：议价比较共享历史与角色隔离；财报研究比较串行与有界并发；紧急插单比较排队、Hook 检查点抢占和独立推进。默认不需要 API Key。

## 启动

要求 Node.js >= 22.13.0。使用本目录的独立依赖与锁文件；无需启动 Financial Agent 的 Python 服务。

```powershell
cd demos/mastra-negotiation
npm ci
npm start
```

打开 http://127.0.0.1:4317 ，点击「运行对照实验」。终端按 Ctrl+C 停止服务。

默认输入：买家最高预算 1000 元、卖家最低底价 800 元、最多 5 轮（每轮双方各行动一次）。

## 用一分钟演示

1. 保持默认「本地模拟」，点击运行。两个模式都会通过真正的 Mastra `Agent.generate()` 执行；模拟的是模型返回内容，不是 Mastra 或审计结果。
2. 默认两组均在第 4 轮以 920 元成交，各调用模型 7 次。共享组隔离检查失败 6 次；隔离组为 0 次。
3. 点击共享组「第 2 轮 · 买家」。完整请求仍包含卖家底价 800 和 `SELLER_PRIVATE_...` 随机标记，标记会高亮。
4. 点击隔离组的同一轮。这里有买家自身的预算与双方的公开报价，但没有卖家私密配置。
5. 导出审计 JSON，查看完整输入、输入哈希、Agent 身份与判断依据。
6. 将预算改为 700、底价改为 900、轮数改为 2：两组均应耗尽轮数，不能产生不可能的成交。

模拟策略刻意只读取最新的自身配置和公开报价，即便共享历史中已经包含对方秘密也不利用它。因此两组成交结果相同。这说明「结果看起来没问题」与「输入是否符合隔离要求」是两项不同的验收标准。

## 比较的定义

| 项目 | shared | isolated |
| --- | --- | --- |
| Mastra Agent 实例 | 1 | 2（buyer / seller） |
| 模型 / 指令 / 输出合同 | 相同 | 相同 |
| 调度 | 买家、卖家交替串行 | 买家、卖家交替串行 |
| 历史 | 一个数组累积双方消息 | 每方一个数组，只累积自身私密消息与公开报价 |
| 工具 / 外部记忆 | 无 | 无 |
| 当前角色能看到的私密配置 | 随角色切换逐渐包含双方配置 | 仅自身配置 |

所有 Agent 均为本次实验新建。两组使用同一组随机私密标记以便比较，不同实验重新生成标记，不共享历史。协调器与实验管理员可以看到双方数据；Agent 模型只收到显式组装的输入。

如果单个逻辑 Agent 切换为彻底隔离的输入与状态，也可以满足此需求。本实验没有证明所有名叫「单 Agent」的方案都失败，只比较明确的共享与隔离拓扑。

## 实际调用和审计位置

```text
浏览器输入
  → Node HTTP API（配置校验、单实验准入）
  → 确定性协调器
  → 组装 shared / buyer / seller 历史
  → Mastra Agent.generate()
  → LanguageModelV3.doGenerate() 审计：完整 prompt、tools、hash、时间
  → 本地 MockLanguageModelV3 或真实兼容 API
  → Zod 输出校验 + 自身价格边界 + 接受报价校验
  → 仅公开动作进入下一方的 publicHistory
```

使用 `@mastra/core` 1.64.0 的 Agent API。控制流很短，直接用确定性循环，不额外引入 DAG、数据库或 Mastra Studio。

- `src/domain.js`：输入与公开动作合同、上下文组装、私密字段审计。
- `src/models.js`：模拟策略、真实模型适配器、模型调用拦截器。
- `src/experiment.js`：两种执行方式、角色历史、串行调度、成交判定、调用记录。
- `src/server.js`：本地 HTTP 服务，静态界面与比较 API。
- `public/`：中文比较界面、完整请求查看与 JSON 导出。
- `test/`：领域合同、Mastra 集成、真实 HTTP 适配器及本地服务测试。

`inspectPrompt()` 检查当前角色配置是否存在、对方结构化私密配置是否存在、对方随机标记是否出现；判断由实际捕获的数据推导，没有按模式硬编码通过/失败。公开价格等于对方底价不算私密配置泄漏。

随机标记检测是辅助证据，不是语义防泄漏系统。它不能排除从公开报价推断底价、数字侧信道或供应商内部的数据处理。这里仅证明应用组装并发送的输入边界。两 Agent 在同一 Node 进程运行，共用服务账户环境；未实现进程、凭证或租户级隔离。

自由解释文本被限制为四个固定原因代码（opening、counter、acceptable、no_agreement），避免把整段自由生成文字直接传给对方。额外字段、非法价格、错误接受动作会被拒绝，原始输出仍保存在管理员审计中。报价本身仍可能透露偏好，不声称完全保密或博弈论安全。

## 接入真实模型

在本目录复制 `.env.example` 为 `.env`，设置三个变量并重启服务：

```dotenv
NEGOTIATION_BASE_URL=https://your-provider.example/v1
NEGOTIATION_MODEL=your-model-id
NEGOTIATION_API_KEY=your-api-key
```

端点须兼容 `/chat/completions`。界面在三个变量齐全时开放「真实模型」。仅加载本 Demo 的 `.env`，不读取父仓库密钥；请求体不能指定端点或密钥。

议价两组仍使用同一个模型。温度设为 0，单次输出上限 300 token、无自动重试、每组最多 10 次调用。HTTP 服务一次只允许一个比较，单调用超时 30 秒、全实验超时 180 秒；议价场景关闭页面会取消待进行工作。取消无法撤销已发生的供应商调用或计费。财报场景的后台执行与恢复规则见下文。

真实模型可能输出非法 JSON、提出越界价格或提前退出。系统会保留错误记录，把该组标为 `incomplete`，不会悄悄换成模拟结果。接入不支持这些参数的模型可能失败，需要针对该供应商调整适配器。

真实模式还捕获最终 HTTP 请求体和哈希，以核对 SDK 模型输入与最终发送的 messages。不会记录 Authorization 请求头或 API Key。模拟模式没有网络请求，因此只声称捕获模型适配器入口。

真实模型的报价路径和调用次数可能不同；不保证两组实际 token、成本或成交结果一致。本 Demo 没有评估准确率或谈判质量，也没有统计显著性结论。

## 本地 API

- `GET /api/config`：返回框架版本、真实模型是否已配置、模型名称、轮数上限。没有密钥。
- `POST /api/compare`：请求 `{ "buyerMax": 1000, "sellerMin": 800, "rounds": 5, "backend": "fixture" }`。字段可省略以使用默认值。
- 返回 `shared`、`isolated`、逐调用 `calls`、公开报价、模拟私密配置、协议元数据、输入审计结果。API 是本地实验管理员视图，不适合作为真实买卖双方接口。
- 错误：400 输入/真实模型配置错误；403 非本地来源；409 已有实验运行；413 请求过大；500 执行异常。每组内部失败体现在结果的 `status: error` 和 `audit.result: incomplete`。

服务只绑定 `127.0.0.1`。议价场景不持久化原始提示，刷新页面丢失当前显示结果；需要保留时使用「导出审计 JSON」。财报场景会保存任务及提示。不要将该管理员服务直接暴露到公网。

## 场景二：三份财报，并行与恢复

打开 http://127.0.0.1:4317/#research ，或点击「02 · 财报研究 / 并行与恢复」。三份财报全部虚构，分别提取营收、同比、风险和逐字引用；确定性校验器对照固定材料检查结果。它不是通用财报事实核查器。

1. 保持并发上限 3、每份模拟等待 3 秒，运行对照。两组依次执行，串行约 9 秒、并行约 3 秒，总等待约 12 秒。时间线读取真实任务时间戳，不预设成绩。
2. 将并发上限设为 1，观察并行组也退化为串行等待。上限为 2 时，第三项要等一个执行槽空闲。
3. 勾选「让 B 公司首次检索超时」再运行：两组均保存 A/C，B 标为可重试，不会把失败当作零营收。
4. 点击「只重试失败任务」：两组都只追加 B 的尝试，A/C 的结果与尝试 ID 不变；尝试次数为 A=1、B=2、C=1。时间线单列重试批次。
5. 点击公司卡片，核对原文、模型输入、输出、Agent ID、尝试 ID 和输入哈希。刷新可恢复最近一次研究，导出可取得完整 JSON。

| 控制项 | 串行组 | 并行组 |
| --- | --- | --- |
| Agent | 每批复用 1 个实例 | 每批至多 N 个同模板实例 |
| 模型、提示、材料、校验规则 | 相同 | 相同 |
| 单次上下文 | 仅当前公司材料 | 仅当前公司材料 |
| 调度 | A → B → C | 至多 N 项同时执行，按 A/B/C 汇总 |
| 成功保存、失败重试 | 支持 | 支持 |

**证明边界：**加速来自独立任务的等待重叠，普通异步模型调用也能获得这种收益；没有证明多 Agent 更会研究，也没有证明并发只能由多 Agent 实现。两组使用相同的持久化机制，因此局部重试不是多 Agent 专属优势。所有 Agent 在同一 Node 进程里，不具备独立进程的失败域。

### 模型与任务账本

- 默认是本地确定性模拟模型，但实际经过 Mastra `Agent.generate()` 与模型入口审计。模拟模型按固定格式提取材料，不衡量 LLM 的准确率。
- 真实模式复用上述三个 `NEGOTIATION_*` 配置；初次最多 6 次模型调用，单次上限 600 token，无自动模型重试，单次超时 30 秒。每轮后台执行上限 180 秒。B 的注入超时发生在模型调用之前。
- **本地和真实模式都有相同的人为检索等待**，所以真实模式耗时也不能直接当供应商性能基准；本次没有调用外部付费模型。
- `artifacts/research/<run UUID>.json` 保存任务状态、材料、提示、调用记录、输出和尝试历史。临时文件写完后原子重命名；目录已被 Git 忽略。这里没有 `fsync` 断电耐久性保证。
- 研究在后台运行，关闭或刷新页面不会取消。浏览器只用 localStorage 保存最近的运行 ID。重启服务后读取未完成账本，会把执行中任务转为可重试，保留已成功产物；需点击重试继续，不自动续跑。未开始的任务也会被领取。
- 账本由单个服务进程拥有，没有跨进程锁、分布式租约或 fencing；不要让多个服务共享该目录。仅面向本地演示，不是生产任务队列。真实模型配置在重试前应保持不变。

### 研究 API

- `POST /api/research/runs`：`{ "concurrency": 3, "delayMs": 3000, "failB": false, "backend": "fixture" }`，字段可省略。返回 202 和运行快照，后台继续执行。并发范围 1–3；等待范围 10–5000 ms（界面提供 1/3/5 秒）。
- `GET /api/research/runs/:uuid`：返回持久化运行快照。运行状态为 `running`、`completed`、`partial` 或 `error`；任务状态为 `pending`、`running`、`succeeded` 或 `failed_retryable`。
- `POST /api/research/runs/:uuid/retry`：请求 `{}`，返回 202；仅领取尚未开始或可重试的任务，不重做成功项。
- 错误包含 400 参数/UUID/真实模型配置错误、404 找不到运行、409 实验忙或没有可重试任务。研究与议价共用单实验准入，不能同时启动两个比较。
- `src/research.js` 实现研究合同、模拟材料、调度、校验和账本；`public/research.js` 实现标签页、轮询、实测时间线、重试与导出。

## 场景三：持续研究＋紧急插单

打开 http://127.0.0.1:4317/#interrupt 。三组同时开始相同的研究，收到同一份虚构业绩预警，核查后输出相同的风险代码与公告引文。

| 方案 | 执行规则 | 资源 |
| --- | --- | --- |
| queue | 研究全部完成，才领取预警 | 1 个 Agent、1 个执行循环 |
| hook | 每一步结束检查事件，处理预警后从下一步恢复 | 1 个 Agent、1 个执行循环＋内存检查点 |
| independent | 研究与预警分别推进，允许时间重叠 | 2 个同模板 Agent、2 个异步执行循环 |

### 操作方式

1. 默认研究净等待 60 秒，第 10 秒自动发送预警；预警净等待 1 秒，完成期限为事件到达后 5 秒。可改为 12 秒快速模式，第 2 秒自动发送。
2. 默认检查间隔 1 秒，Hook 通常也能按时响应，但研究会暂停约一次预警处理的时间。独立组不为预警主动暂停研究。
3. 在快速模式把检查间隔改为 6 秒：预警到达时，Hook 要等当前步骤结束，约排队 4 秒，再处理约 1 秒。是否超期按实际时间判定，不能保证精确边界在每台机器上得到相同结果。
4. 可在自动事件之前点击「立即发送紧急事件」。三组收到同一时间戳的事件，手动发送后取消自动注入；每次运行只发送一次。
5. 观察共用时间刻度上的绿色研究段、棕色预警段、事件到达黑线和截止红虚线。Hook 的研究条在处理预警时有空隙，独立组的两条任务会重叠。可展开完整模型请求和检查点，或导出 JSON。

### 公平性与限制

- 同一次运行的三组具有相同研究步骤数、单步等待、预警等待、模型、提示与输出规则；每次输入按任务组装，并显式传入已完成步骤。Agent 不依赖隐藏历史。
- 改检查间隔会改变研究分段数和模型调用次数，所以应在同一次运行内比较三组，不能把不同间隔运行之间的耗时差全部归因于抢占。
- 使用本地确定性模拟模型，但实际执行 Mastra `Agent.generate()` 并在模型入口捕获请求、Agent ID、输出与哈希。研究产物是编号片段，不是真实主题研究；不支持本场景的外部真实模型调用，也没有真实交易。
- 人为等待模拟一个不可中断的工作步骤。这里的 Hook 是步骤边界上的应用调度检查，不是 Mastra 内置插件，也不是能打断进行中模型调用的 OS 抢占。若实际任务可取消、可重入，单循环可以设计更细的抢占策略。
- 独立推进消耗额外并发资源；普通 worker 或并行模型调用也能实现。同进程、不提供独立失败域，不证明多 Agent 更聪明或是唯一实现方式。
- 三组在一个进程同时运行，有共享 CPU 的干扰；模型调用和调度开销计入实测，净等待不等于总耗时。不保证生产供应商限流条件下的 SLO，不是实时系统证明。
- `responseMs` 是事件到预警成功完成；`queueMs` 是到预警任务开始；`pauseMs` 只计 Hook 为预警主动暂停研究的时间；`researchElapsedMs` 是研究从运行开始到全部步骤完成的墙钟耗时。后端使用单调时钟差值，不用硬编码成绩。
- 记录仅保存在服务内存，最多保留最近 10 次运行，启动新运行时淘汰最旧记录。页面会话保存运行 ID，刷新可重新读取同一服务中的记录；重启服务即丢失，需提前导出。关闭页面不取消后台工作。

### 插单 API

- `POST /api/interrupt/runs`：返回 202 和快照。默认请求 `{ "researchMs":60000, "stepMs":1000, "alertMs":1000, "autoAfterMs":10000, "deadlineMs":5000 }`，所有字段可省略。研究范围 100–60000 ms，步骤 10–10000 ms 且整除研究时长，至多 120 步；预警 10–3000 ms，期限 10–10000 ms，自动事件至少 10 ms 且早于研究净等待结束。
- `GET /api/interrupt/runs/:id`：读取快照，状态为 `running`、`completed` 或 `error`。响应包含三组的步骤、调用审计、事件、指标与输出。
- `POST /api/interrupt/runs/:id/event`：请求必须为 `{}`；返回 202。允许在研究执行期间注入，不受“禁止启动第二个实验”的准入限制；重复发送返回 409。
- 400 参数错误，404 运行不存在，409 实验忙、事件已发送或运行不再活跃。三场景共用单实验启动准入；一次插单对照内部允许三组并发执行。
- 单轮后台执行有 90 秒超时信号，无自动重试。`src/interrupt.js` 实现调度与审计；`public/interrupt.js` 和 `public/interrupt.css` 实现页面。

## 验证记录

```powershell
npm test
npm run check
```

开发遵循仓库 TDD：先建立领域与执行/API 空实现及行为测试，实际观察缺少实现导致的 RED，再实现并观察 GREEN。额外的 HTTP 适配器与异常场景测试是回归证据，不称为 TDD RED。
